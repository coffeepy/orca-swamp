# Architecture

Notes for people who work on the plugin. For what it does and how to install it, see the [README](../README.md).

A right-sidebar panel that shows the swamp workflows of the focused workspace's repo, lets you approve or reject waiting gates, and hands a failed run to an agent terminal. The panel is an HTML page (`src/app.ts`, styled from Orca's `--orca-*` theme variables) that polls its worker (`src/worker.ts`) every 10 s, or every 2 s while a run is moving. The worker runs `~/.local/bin/swamp --json` (`src/swamp.ts`) and parses its output (`src/domain.ts`); `src/present.ts` holds the pill, time and command strings the page shows. `src/repo.ts` finds the focused workspace's folder through one of its terminals (`orca terminal show`), finds the repo at or above that folder or registered below it, and a repo picked in the panel is remembered per workspace folder in `~/.config/swampling/pins.json`. A workspace with no terminal is matched by name and branch; when several share them, the panel asks instead of guessing. After an approve, the worker starts `swamp workflow resume --run <id>` in the background. The panel keeps the last place (tab, run, factory or ticket) of each repo in its `localStorage`, for the 20 repos used last, so a switch back to a repo opens where you were.

A workspace change shows the last known answer at once and asks again behind it; the Refresh icon turns meanwhile. The panel keeps each workspace's last resolution in `localStorage` (the 20 used last) and each repo's last read data in memory (the 10 left last), and puts a repo's data away whenever another repo takes the screen, so one repo's data never shows under another's header. The worker remembers its slow lookups for its life: swamp's workspace registry (read again behind an answer once it is 30 s old), the workspace of each terminal, and the remote repos (60 s, never an answer with a problem). The registry is read while Orca and the remote hosts are asked. The Refresh button sends `repo.resolve` with `fresh: true`, which reads all of them again. A workspace never seen shows "Loading…" as before.

Repos on remote hosts work too. For a focused workspace on a remote Orca server, Orca answers `workspace.readContext` with null, or with a name that `workspace.list` does not hold. In the two cases the panel asks the `orca` CLI (`src/remote.ts`) for every saved server's workspaces and the SSH host Orca deployed each server through, finds their swamp repos over SSH in one call per host, and offers them in the picker. While a remote host is paired, such a workspace is offered the remote repos only, not the repos of this Mac. With a name, the one remote workspace of that name and branch gives the repo without a pick, and a pick is remembered for that name; with null, the pick is remembered for all remote workspaces. Every swamp call for a remote repo runs as `ssh -o BatchMode=yes <host> sh -s` with the script on stdin and each argument quoted for `sh`, so a csh or fish login shell never parses a value; calls share one connection per host for a minute. A host that needs a password or key prompt shows the exact `ssh` command to try. Studio is off for remote repos (it would need a port forward), and Send failure needs a terminal Orca names, which it does not for remote workspaces.

A Factories tab shows StageCraft factories (`src/stagecraft.ts` parses them). It checks for the extension with `swamp model type search stagecraft`, and a repo without it gets an explainer with the install command instead of an error. The board reads every work item's `run` record with one `swamp data query`; a work item's page reads its run, pinned definition, products and metrics with another. Approve runs the work item's `approve` method on the person's behalf and, when that was the last gate the exit waited on, `advance` on that exit; Decline runs `decline`. Studio starts `studio serve` (creating the studio model on first use) and opens the URL it logs in the browser.

Every work item carries one `Reason` (`src/stagecraft.ts`): why it is where it is. `reasonOf` derives it from the run record the board and the work item page already read, so it costs no swamp call. The reasons are `gate` (an exit waits for a person), `parked` (at the dispatch cap), `working` (the stage entry's latest dispatch has no outcome), `failed` and `interrupted` (that dispatch ended so, with the reason its driver wrote), `passed` (it succeeded and nothing advanced the ticket), `idle` (nothing was dispatched for this stage entry) and `done`. A ticket's status is read off its reason through one table, so `failed` and `interrupted` count as stuck. `whyHere` and `reasonWord` in `src/present.ts` turn a reason into the sentence on the work item page and the word on the board. StageCraft records which workflow a workflow stage's dispatch ran but not the run's id, so `dispatchRun` picks the first run of that workflow started after the dispatch, from the run list the panel holds when the Workflows tab was read; without it the button opens the workflow's latest run. Whether the process behind an open dispatch still lives is not known: a dispatch record holds no pid.

The Needs you tab is the one view that belongs to no repo (`src/inbox.ts`). Its repos are, once each: the repo at or above the folder of each Orca workspace on this Mac, the repos in swamp's registry on this Mac, each repo in `pins.json`, and each repo the panel showed since the worker started. Pins are the only way a remote repo gets in, so a remote repo counts once it was picked in some workspace or shown on screen. For each repo the worker runs `swamp workflow approvals` and one `swamp data query` for the work items' `run` records, all repos at once; a repo that fails or times out (20 s per swamp call) is named in the answer and the others still show. The worker remembers the answer for 30 s, and the panel asks every 30 s while the tab shows and once a minute for the badge. Open on an item of another repo puts that repo on screen without a change to the workspace's pick, under a bar that says so, until Back or a change of workspace.

A run's screen has controls that change the run. `runActions` in `src/domain.ts` holds the one table of which actions a run status offers: Stop (`swamp workflow cancel <workflow> --run <id>`) for a pending, running or suspended run; Retry (`swamp workflow resume <workflow> --run <id>`, with `--from <step> --job <job>` from one step) for a failed run, or a suspended one with no gate to decide; Recover and resume (`swamp workflow recover <workflow> --run <id> --acknowledge-unknown`, then resume) for an interrupted one; and Run again for a finished one. Run (`swamp workflow run <workflow> --input <name>:json=<value>`) reads the workflow's input schema from `swamp workflow get` and shows a form when it declares inputs. `swamp workflow run` and `resume` end only when the run does, and `--detach` needs a `swamp serve` server, so the worker starts both in the background (`startBackground` in `src/swamp.ts`, `nohup` on a remote host) and then reads the run twice a second, for 10 s at most, until swamp lists the new run or the retried run changes status. If swamp refuses, the button shows what it said. A `run` or `resume` that exits with an error and no words has run the workflow to a failed end, which the run's own screen shows. The worker handlers are `workflow.inputs`, `run.start` and `run.act`; they check every name the panel sends, check a form's input names against the workflow's own, and pass each value to swamp as one argument.

Whether work in flight is healthy is answered by `src/pace.ts`, and every threshold of it is in `PACE` there. `usualTimes` gives each workflow's usual time: the median duration of its 20 newest passed runs, or none for fewer than 3. It reads the run list the Workflows tab already holds, so it costs no swamp call. `paceOf` turns a running or pending run into one `Pace`: `on-pace`, `slow` (it took twice the usual time), `quiet` (no activity for longer than the usual time, and for 10 minutes at least) or `gone` (its swamp process no longer exists). `PACE_LOOK` in `src/present.ts` is the one table of how each reads. A run's last activity is the latest time one of its steps or jobs began or ended, which `run.get` already answers. For a repo on this machine the worker also reads the run's own files (`runVitals` in `src/swamp.ts`): the later change time of its record and its log, and the `pid:` its record names, checked with signal 0. That is how swamp itself tells a run cut off, and swamp keeps the status `running` after the process dies, so a dead pid is the only sign. The files are read for the runs in flight only, on `workflows.list` and `run.get`, with no swamp call. A remote repo's run gets no process check and no file times: its rows show the elapsed and usual time, and its screen judges quiet by step times alone. A step has no usual time of its own, because past step durations would cost one `swamp workflow history get` per past run. swamp's run list does not mark a run that failed and was retried, so such a run counts in the median with its wait included.

A run's screen follows the run's log (`src/log.ts`). swamp appends one line to the run's `.log` file per event while the run moves, in the shape `<ISO time> [INF|WRN|ERR] model·method·run·<model>·<method>: <message>`, where the message is plain text or one JSON string and may hold color codes. `parseLine` turns a line into a `LogLine` (`at`, `level`, `tag`, `text`, and `pos`, the byte offset of its start) and removes every escape and control byte. `tag` is `<model>·<method>`, the same value as a step's `logTag`, which is how a click on a step narrows the log. The log names no step otherwise, so a step whose model name is a template the panel cannot render gets no filter.

The worker handler `log.tail` answers a `LogChunk`: `{ from, next, size, lines, done }`, all byte offsets. The panel sends `after: <next of its last answer>` and gets only whole lines written since; a line with no newline yet waits for the next read. With no cursor it gets the newest 48 KiB, and `before: <from>` pages back ("Show earlier"). A cursor past the end of the file (a log cut short) is answered with the newest lines and `reset`. One answer reads 128 KiB at most, or what `limit` says within 1 to 256 KiB; a longer backlog takes several asks, and a line longer than a read comes in parts. `done` is a run whose record says it ended, read to the end of its log. `logWindow`, `linesOf` and `readChunk` hold that logic with no file access, and take a `ReadLog` that reads bytes.

The file's path is never the panel's to name: the worker builds it with `runFile` from the run id the panel sent and the workflow id swamp gave for that run, and `runFile` refuses an id that is not letters, digits, `-` and `_`. The workflow id is remembered when `run.get` reads the run, so following costs no swamp call. For a repo on this machine one read opens the record for its `status:` line and the log for the bytes: 0.1 ms with nothing new and 3 ms for 128 KiB of a 5 MB log, measured in process. For a remote repo the same read is one `ssh` round trip over the shared connection (`remoteLogScript`: `wc -c`, `sed` for the status, `tail -c +N | head -c L`, with the paths and numbers as quoted words), read as latin1 so each character is one byte and the offsets hold. That replaces `swamp workflow history logs`, which takes 2 to 3 s per call and answers the whole log each time. A repo that keeps its runs outside its `.swamp` folder has no file to read, and the log section says so.

In the panel the log's element is made once and never redrawn. Every other part of the page is still an HTML string replaced on each poll, so `redrawAround` in `src/app.ts` rebuilds the page around the element instead of taking it out and putting it back, which would drop its scroll position and a selection in it. New lines are appended as elements. The panel keeps 3000 lines (`LOG.keepLines`), or 6000 while the person has scrolled up to read. It stops asking once the answer is `done` and the run is not in flight, or the run's process is gone. The time of the newest line also counts as the run's last activity for its pace, which gives a remote repo's run a sign of life between two steps. The step's own Logs tab is older and still reads `swamp workflow history logs` through `logs.get`.

For a ticket, the `working` reason carries `activeAt`, the time of the last journal event of the stage entry (the dispatch, or a later `usage`, `checkpoint` or `recorded`). A working ticket with no event for `PACE.ticketQuietMs` (2 hours) has the status `stuck` while its reason stays `working`, and reads "no activity". In the repos this was built against, the longest ordinary gap between two events inside a dispatch was under an hour, and every ticket open past that had been silent for days.

`orca plugin test .` runs the tests against captured swamp JSON in `src/fixtures/`.


## Files the plugin writes

- `~/.config/swampling/pins.json` holds the repo picked for each workspace.
- `~/.config/swampling/settings.json` holds the theme.
- `~/.config/swampling/ssh/` holds the shared SSH connection sockets for remote repos.

## Environment overrides

- `SWAMPLING_BIN` sets the swamp binary.
- `SWAMPLING_PINS` sets the pins file. The settings file sits beside it.

## Develop

```sh
orca plugin validate .
orca plugin test .         # runs the tests against captured swamp JSON in src/fixtures/
orca plugin dev watch .    # loads this folder into Orca and prints its logs and reloads; Ctrl-C unloads it
```

Orca names the publisher after where the plugin is installed from: the GitHub or GitLab owner of
its repository, or `local` for a folder. See
https://github.com/stablyai/orca/blob/main/docs/reference/plugin-authoring.md.
